# Retail Demand & Inventory Digital Twin

A prototype **Digital Twin** of a retail store network, built for the
Business domain of *"An AI-Based Intelligent Decision Support System for
Digital Twin-Driven Digital Transformation."*

> This is not a sales forecasting dashboard. It is a virtual representation
> of a retail operation whose state evolves according to observed demand,
> AI-based predictions, inventory dynamics, replenishment policies and
> simulated supply conditions. It allows decision-makers to test operational
> scenarios before implementing them in the real business.

## Data

Source: Kaggle *Store Item Demand Forecasting* dataset.

- `train.csv`: 913,000 rows, daily sales, 2013-01-01 to 2017-12-31, 10 stores x 50 items. No missing values, no duplicates.
- `test.csv`: 45,000 rows, 2018-01-01 to 2018-03-31, same stores/items, **no `sales` column** — a true holdout with no ground truth. Only used to define future simulation dates; the twin's "actual" demand for those dates is *simulated* (model prediction + scenario adjustment + noise), never invented as if it were real.

### Observed vs. derived vs. simulated variables

| Layer | Variables | Source |
|---|---|---|
| **Observed** | `date`, `store`, `item`, `sales` | Directly from `train.csv` |
| **Derived (AI)** | calendar features, lag/rolling features, `predicted_demand` | Computed from observed data; XGBoost model output |
| **Simulated** | `inventory`, `pending_orders`, `safety_stock`, `reorder_point`, `actual_demand`, `stockout`, `service_level` | Generated by the twin's policy/state-transition logic — **do not exist in the source dataset** |

## Scenarios

The Scenario Simulator compares a **baseline** (no shock) against a configured disruption. Demand Surge and Combined Disruption expose a **Demand surge (%)** slider from **10% to 100%** (previously fixed at +30%). The twin multiplies forecasted demand by `1 + surge/100` while keeping the stocking policy sized on normal demand, so you can see how service level, stockouts, and health score change as the shock gets more severe. Re-run the simulation after moving the slider.

## Architecture

```
data_utils.py       - loading + feature engineering (shared by training & app)
train_model.py       - standalone XGBoost training script -> models/demand_model.pkl
forecasting.py       - recursive day-by-day demand forecasting for simulation dates
twin.py               - the Digital Twin: per-store-item state machine
                        (inventory, safety stock, reorder point, pending orders,
                         event log) + network-level DigitalTwin container
simulation.py         - scenario orchestration, baseline-vs-scenario comparison,
                        Business Operational Health score, critical-entity ranking,
                        dss_evidence.json export
recommendations.py    - rule-based, metrics-grounded recommendation engine
app.py                - Streamlit UI (4 pages)
```

### State-transition logic (per store-item, per simulated day)

```
1. Receive any orders arriving today       -> inventory += arriving_qty
2. Simulated demand = predicted_demand * scenario_demand_multiplier + noise
3. Fulfill from inventory (floored at 0)   -> fulfilled, unmet tracked
4. If inventory <= reorder_point           -> place replenishment order
                                               (arrives after supplier lead time)
5. Record inventory/demand/service-level history + event log
```

Reorder point and safety stock are sized using **baseline** demand and lead
time (not the scenario's disrupted values) — a retailer's stocking policy is
fixed before a disruption hits, not adapted in advance. This keeps
baseline-vs-scenario a fair, like-for-like comparison.

```
Safety Stock   = z(service_level) * demand_std * sqrt(lead_time)
Reorder Point  = avg_daily_demand * lead_time + Safety Stock
```

## Setup

```bash
pip install -r requirements.txt

# 1. Train the demand model (only needs to be run once)
python train_model.py

# 2. Launch the app
streamlit run app.py
```

## Business Operational Health score (0-100)

Transparent, documented in `simulation.business_health_score()`:

```
score = 25 (base offset)
      + 60 * service_level
      - 25 * min(2 * critical_store_item_rate, 1)   [stockout risk penalty]
      - 10 * min(5 * unmet_demand_ratio, 1)          [unmet demand penalty]
      + 15 * (1 - inventory_volatility_ratio/3)      [inventory stability]
```

## DSS evidence output

The "Decision Support Evidence" page exports `outputs/dss_evidence.json`,
containing the model's validation metrics, baseline and scenario aggregates,
their comparison, ranked critical store-item pairs, and grounded
recommendations — structured for consumption by the overarching DT-readiness
DSS. No DT-readiness score is computed here; that's the overarching DSS's job.

## Design constraints honored

- No invented observed data; inventory/supplier fields are clearly simulated.
- No financial/profit metrics (not present in the source data).
- No LLM-generated recommendations — every recommendation cites an actual
  simulation metric and its change.
- Model trained offline (`train_model.py`); the app only loads the saved
  `.pkl`, it never retrains on Streamlit startup.
